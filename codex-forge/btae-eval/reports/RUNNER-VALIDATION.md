## 首轮问题及修正，不覆盖历史

1. 最初13项运行器测试中12项通过、1项失败：取消测试用固定延迟触发，Worker 可能尚未创建心跳。改为等待真实心跳再发取消，随后测试通过；验证了有子进程存活时的清理行为。
2. 第一批 runner-v1 产物复核发现：retry 的 episode 为1505ms，原限额1500ms，但旧汇总为 completed。原因是代码快照/文件清点耗时未参与最后一次截止判断。已纳入这一开销，并加入回归测试：Worker 成功但封存前超时仍不能汇总为完成；取消/协议错误等既定原因保持不变。
3. 原12个产物完全保留。新验证器对 runner-v1/retry 返回非零，明确拒绝该过期完成记录；其余11个仍可验证。runner-v1/timeout 在200ms预算下可能导出阶段就耗尽，记录 attempts=0；它只证明准备阶段预算失败，**不作为杀进程证据**。真正进程超时由测试和 runner-v2 的已启动案例验证。
4. 修正后的 runner-v2 使用适合本机磁盘封存开销的诊断限额；12例均启动了 Worker，完成状态的 elapsed_ms 均在该例时限内。增大的是诊断时限，不改正式 Pilot 的60000 token/1800秒候选预算，也不把第二批成功覆盖为第一批成功。

旧摘要原样保存在 [runner-validation-v1.json](runner-validation-v1.json)。当前报告明确是实现纠错后的验证结果。

## 信任和功能边界

这些运行不是模型任务，data_kind 固定 runner_diagnostic_only；隐藏测试和真实任务成功字段恒为 null。诊断记录不能按正式 Observation 的类型反序列化。因此31项测试和12个诊断成功都不能用于 BTAE 效果统计。

usage 是假 Worker 协议自报，只用于测试监督器；没有价格数据或服务商可信计量。达到上报检查点时可能已经超过 token 限额，记录实际超额并停止，不能宣称预防了每一个超额 token。

凭据的哈希清单和启动/终态交叉检查用于可信主控上的误改检测。没有数字签名或不可变外部账本，不能抵御有权限重写整套证据的恶意宿主。中断后只识别未完成凭据，不自动依靠旧 PID 认领进程或恢复任务。

只验证了 Linux 本机 Bubblewrap 路径；没有验证其他平台、生产 seccomp、磁盘配额、内存/CPU cgroup 或不可信 Worker 的完整资源防护。每个日志与消息有大小上限，代码快照拒绝符号链接/特殊文件/过大单文件，异常时保留未完成凭据。当前诊断只支持第1轮种子导出，后续轨迹不会偷偷从原始代码重跑。

下一步是实现正式 DSH 协议适配与可信收集，再落实方法机制和独立真值审核；现有诊断隔离通过不自动等价于将来具有网络、凭据或 MCP 工具的真实执行路径通过。
